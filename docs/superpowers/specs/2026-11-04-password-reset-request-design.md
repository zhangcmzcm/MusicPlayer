## 1. 范围及已确认原则

唯一接口：`POST /api/v1/users/password-reset-requests`。用户忘记密码后，输入已绑定邮箱，无需登录、旧密码或近期auth_time，申请找回密码专用验证码。USER、ADMIN账户适用相同规则；未绑定邮箱的账户暂不支持自助找回，不增加其他人工恢复渠道。

整体采用两步流程：本接口申请发码；后续独立接口提交challengeId、验证码及新密码完成重置。后续接口的方法、路径、确认额度、消费及MySQL更新细节另行设计、审核，本轮不实现。已确认的衔接原则为：验证码5分钟到期、累计错误5次失效、正确码一次性消费；申请绑定账户、受理快照邮箱和token_version。重置成功时同事务修改密码并递增版本，撤销全部旧登录，不自动签Token。新密码沿用现有8—72个ASCII可打印字符、非全空格、保留首尾空格且不能与当前密码等价的规则。

本轮交付范围包含申请端点直接依赖的Redis任务队列、后台领取/发信/激活/过期清理、配置、测试及API/部署文档；后台处理不是第二个HTTP接口。不新增查询申请、重发专用、恢复、取消或重置确认端点，不扩展现有通用REGISTER/LOGIN发码用途，不改既有改密、改邮箱和再次验证业务契约。

## 2. 方案比较与选择

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| Redis保存任务、后台发信（选定） | 受理链路统一限流、查询快照、生成标识、入队并返回202；后台发送并激活 | HTTP不等待SMTP；需要有界队列、跨实例领取、任务终态及清理机制，无需引入消息中间件 |
| 同步发信、统一202 | 等待SMTP结束后统一响应 | 接近既有实现，但真实账户耗时暴露SMTP差异，不采用 |

用户已选择：独立两步流程、随机challengeId、不暴露账户不存在、成功发信后才替换旧有效码、不自动重发、仅保留最新待处理申请、受理时读取账户快照。

先前“后台才首次查询账户”的表述已明确由受理时读取快照替代。否则排队期间的凭据变更可能让旧申请绑定变更后的版本，违反申请版本绑定原则。所有合法邮箱均执行候选查询；后台重新核对，不把查询留到首次发送时。

统一响应减少账户枚举信息，不承诺所有分支纳秒级等时。数据库查询、系统故障及资源竞争仍可能造成耗时差异；不以sleep伪造等时，不引入只对真实账户执行的SMTP等待或可查询状态。

## 3. HTTP契约

```http
POST /api/v1/users/password-reset-requests
Content-Type: application/json

{"email":"alice@example.com"}
```

路径使用users，因为属于账户密码管理；不使用me，因为没有已认证本人上下文。公开放行仅新增此Method+Path，保持其他端点权限。正常调用不发送Authorization；若主动附带无效Bearer，允许现有认证链提前拒绝，不绕过JWT版本/签名校验。

仅允许email字段一次且必须为字符串，禁止userId、角色、purpose等字段。缺体、null、数组、嵌套、非字符串、未知或重复键（包括转义同名）、多根及尾随非空白均400。只接受application/json，省略charset或显式UTF-8；缺少/错误媒体类型、其他charset为415。正文严格UTF-8，有界读取最多16385字节检测超限，16384字节预算包含尾随空白，不信任Content-Length。

邮箱沿用现有规则：拒绝CR/LF和孤立UTF-16代理字符；trim后Locale.ROOT小写，非空、最多120个Java字符，经Bean Validation及严格单邮箱地址校验。拒绝显示名称、地址组等形式。不为本接口改变已有邮箱存储规则。

成功返回202 Accepted，Cache-Control: no-store，无Location、Token、账户ID、掩码邮箱、是否发送字段或SMTP标识：

```json
{
  "challengeId": "AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8",
  "expiresAt": "2026-11-04T12:05:00Z"
}
```

challengeId由SecureRandom生成32字节、规范Base64URL无填充43字符；Redis保存其SHA-256摘要，不保存完整原值。每次可靠受理独立生成，不以邮箱、账户ID或时间推导。expiresAt使用Redis受理时间加300秒，UTC ISO-8601，所有任务格式一致。202仅表示任务可靠入队，不表示账户存在、任务已处理或邮件已发送。

## 4. 受理顺序及账户定位

1. 严格解析并规范化输入，解析失败不消耗业务额度。
2. Redis原子执行独立邮箱/IP限流，记录本次受理时间和deadline。所有合法邮箱相同处理，先限流后查询，后续失败不退款。
3. 短只读事务按邮箱读取最小账户投影，不加载Entity或密码摘要。MySQL排序规则命中的候选必须再在Java中核对：数据库绑定邮箱规范化后与输入精确相等。重音等仅数据库排序规则相等而规范化文本不同的候选视为无匹配账户，绝不发往另一个地址。
4. 有账户任务保存userId、原始/规范化绑定邮箱、token_version及必要账户角色校验信息；无账户任务保存明确内部无账户状态。二者不影响HTTP字段或入队规则，不给未来新注册的同邮箱账户补发本任务。
5. 生成标识并通过Redis脚本原子保存任务、更新最新待处理指针和队列成员。入队必须检查deadline仍未到；已过期不返回202。以步骤2的Redis准入时间确定同邮箱申请先后，不以数据库查询完成顺序决定；早先申请慢查询后迟到入队，不得覆盖已入队的新申请，安全拒绝503且不退款。最新准入时间标记保留到对应原deadline，即使新任务已经结束也防止更早申请回写。替换旧排队任务、容量判断及新增必须原子完成，拒绝时不部分覆盖原指针。
6. 明确入队成功才返回202。Redis命令执行后丢失回包为503，可能实际已入队；不自动重试、不退款、不恢复旧待处理任务。

投影中账户数据缺失或损坏属于存储故障，安全失败503，不假设不存在。历史空白/未绑定邮箱不匹配；查询使用现有邮箱唯一索引等值定位，utf8mb4_0900_ai_ci为NO PAD，含首尾空格的历史存储地址不能命中规范化输入，按无匹配处理，统一202但不发信。大小写变体可命中并规范化；重音变体命中后须通过规范化文本精确比对。不得通过全表LOWER/TRIM扫描扩大历史地址覆盖，若需支持另行规划。仅向经严格校验的数据库绑定地址规范化结果发送。受理过程不修改用户表、不递增版本、不撤销登录。

## 5. 独立限流

| 维度 | 额度 |
| --- | --- |
| 规范化邮箱冷却 | 60秒最多1次 |
| 规范化邮箱UTC日额度 | 每UTC日最多10次 |
| 客户端IP | 固定60秒窗口最多5次 |

所有额度采用新找回密码命名空间，与注册、登录、再次验证、改邮箱及普通改密隔离。直接部署使用TCP remoteAddr，复用ClientIpResolver，不接受伪造转发头。邮箱/IP键使用摘要，日志不输出原值。

Lua以Redis TIME统一计算受理时间、冷却、UTC日边界及deadline，拒绝不增加任何维度、不延长窗口。多个维度同时超限时Retry-After取全部受阻维度所需等待的最大值，向上取整至少1秒；不返回账户相关scope。额度写入必须全有或全无，不因执行顺序部分扣减。Redis状态损坏、无TTL或超时关闭放行，503，不删键后放行。

数据库失败、队列满、无账户、替换、发信失败、任务过期或激活失败均不退已消费额度。重新登录、重置或重发不清额度。冷却与后续队列入队是明确的两个阶段：允许扣额后未入队，不宣称跨数据库/Redis分布式原子受理。

## 6. 队列、任务及容量

采用单Redis实例上的原子Lua协议，不承诺Redis Cluster跨槽兼容。专用命名空间可按`music:auth:password-reset:*`组织：邮箱最新待处理指针、任务摘要记录、就绪索引、未结束任务到期索引、有效验证码及限流键。队列与摘要键协议不得拼接邮箱明文或日志敏感数据。

任务记录包含schema版本、challenge摘要、邮箱摘要及投递目标、受理时间/deadline、可选账户快照、处理状态；不保存验证码明文、密码或Token。所有完整性校验失败均不得继续发信/激活；记录与指针的TTL不超过原deadline。后续确认可按challenge摘要定位有效申请，无需客户端重复提交邮箱；具体兑换协议由后续单接口设计。

默认全局1000个未结束任务，覆盖排队及处理中；每实例4路发送，单次SMTP等待上限20秒。三项外部化、正数校验，记录到部署文档，不无界排队或无限建线程。队列满返回503，不驱逐其他邮箱的有效任务。进程重启不清队列或放宽额度，应用内执行器只接收已有持久任务，不作为受理成功依据。

同邮箱新任务替换旧待处理指针，但不触碰ACTIVE。旧任务未领取时可原子终止并释放容量；已领取时标为失去最新资格，保留其未结束容量至完成或原deadline，避免仍在发信却提前释放槽位。新任务如不能在容量约束内加入，则原子拒绝，不取消原任务。

跨实例领取必须原子从可领取状态变为已领取，一次任务最多一个执行者；领取结果未知时调用方不得发送。领取前崩溃且命令未执行的任务仍可被其他执行者正常领取；领取已执行或发送中崩溃的任务不接管、不重新投递，待原deadline过期释放。不存在租约到期后重投机制。

过期清理使用到期索引和有界批次，定期及受理/领取时清理已到期成员；哈希TTL不能替代索引回收。清理只按完整归属删除自身指针，不能删除新任务或ACTIVE。若批次限制导致积压，可暂时503，禁止为腾容量删除未过期任务。处理中任务过期不再激活，即使SMTP线程后来返回。维护不依赖人工删键，不增加公开调试接口。

Redis任务保存不等价于数据库级永久投递保证：依赖Redis持久化、备份和单实例运行条件，故障恢复可能丢失已受理任务，客户端只能重新申请；不承诺exactly-once邮件送达。

## 7. 后台发送与激活

逻辑阶段：QUEUED → CLAIMED → PREPARED → 明确发送成功后ACTIVE；各阶段也可结束为无账户、失效、发送失败或过期。终态不可重回待发送，不自动重试发信。任务完成与ACTIVE申请分离：有效申请继续存活至原deadline，不占未结束任务容量。

1. 原子领取，并确认仍是最新待处理申请、未过期；无账户任务结束且不执行SMTP，不据此修改ACTIVE。
2. 用短只读事务复核账户仍存在、原始绑定邮箱及版本与受理快照相符、账户角色状态有效。普通登录、再次验证不改变版本，不失效申请；改密、换邮箱、角色变化导致版本变化时失效。
3. 生成6位ASCII数字验证码，允许前导零，BCrypt在事务外计算；准备状态仅保存摘要、原deadline及绑定。验证码明文仅在本次执行内存和邮件调用中存在，不落Redis任务、日志或异常链。
4. 有界SMTP发送专用找回密码邮件，与其他用途隔离。邮件注明有效期及以最新申请为准，不含challengeId、密码或Token。用户将邮箱中的code与前端持有的challengeId配对。
5. 明确发送成功后重新读取账户快照，再以Redis原子操作验证最新指针、已领取归属、PREPARED及原deadline，激活新码并替换旧ACTIVE，累计错误从0开始。不得延长有效期。
6. 结束任务释放容量，仅清理属于自己的pending。终止、异常及迟到完成不能清理或覆盖新任务和ACTIVE。

数据库与Redis不构成事务。最终DB复核之后仍可能发生凭据变更；即便随后激活，申请绑定的旧版本也不能在未来确认时兑换。未来确认接口必须再次读取账户并条件更新，不能把ACTIVE存在视为永久授权。本接口不持有数据库锁等待SMTP或Redis，不改用户数据来锁定申请。

SMTP拒绝、超时、中断、进程退出或结果未知均不激活，不自动重发，保留原有效码直到其本来期限。超时或崩溃时邮件可能实际已投递，不能保证用户收不到不可用码。明确SMTP成功也不等价于最终送达邮箱。发送成功但激活回包丢失时，新码可能已经激活；不得恢复旧ACTIVE或通过清理删除可能已成功的新ACTIVE，只结束任务及pending归属。

“失败保留旧码”限于尚未执行激活替换的失败；激活结果未知不能承诺旧码仍有效。成功重发只替换找回密码ACTIVE，不影响其他用途的验证码。已消费或过期旧码绝不恢复。

## 8. 错误、安全与可观测性

| HTTP | code | 场景 |
| --- | --- | --- |
| 202 | 无 | 明确成功入队，账户存在与否相同 |
| 400 | VALIDATION_FAILED | 输入、JSON、UTF-8或16384字节预算非法 |
| 415 | UNSUPPORTED_MEDIA_TYPE | 媒体类型或声明字符集不支持 |
| 401/403 | 沿用现有认证授权错误码 | 附带无效Bearer等由既有安全链处理；本公开接口正常无Token请求不要求登录，也无新增角色限制 |
| 429 | PASSWORD_RESET_REQUEST_RATE_LIMITED | 邮箱/IP额度耗尽，带Retry-After |
| 503 | PASSWORD_RESET_REQUEST_UNAVAILABLE | 数据库/Redis/容量/受理期限或结果无法确认 |
| 500 | INTERNAL_ERROR | 未预期异常 |

复用ProblemDetail，application/problem+json及`urn:problem:music:`加既有小写下划线code形式，沿用统一异常处理。成功、MVC错误均no-store；认证链提前拒绝遵循现有认证错误契约，不伪装成业务202。不得为支持新415而改变既有邮箱接口的专用映射与title。

后台无账户、绑定失效、发信失败不能回改HTTP202，不提供状态查询。无账户任务执行相同入队、容量、到期及领取检查；其不生成可兑换ACTIVE。系统性存储故障按503处理，不声称故障期间也绝对隐藏账户存在性。

日志使用SLF4J，保留受理traceId供后台关联；禁止邮箱/IP明文、完整challengeId、验证码/摘要、邮件正文、密码、Token及底层敏感异常链。按脱敏分类记录受理/任务/发送/激活故障，日志与内部状态toString均审查；不扩大Actuator端点暴露。邮件sender隔离配置沿用已有SMTP来源，不硬编码凭据。应用停止停止领取、受控关闭执行器，不把未确认发送恢复为待重试。

## 9. 组件边界与工程影响

- Controller及严格RequestReader：处理HTTP、DTO校验和响应，不做账户定位/排队业务。
- RequestService：协调额度、快照、生成随机标识及入队，明确未知结果不重试。
- SnapshotReader：最小投影、短只读事务、邮箱精确匹配及绑定复核，不加载密码或持锁发信。
- Redis Store及Lua：准入额度、任务入队/领取/准备/激活/结束、容量和过期清理；接口区分成功、失效、限流、损坏/未知，不用模糊布尔值掩盖存储异常。
- 后台Worker及有界投递器：任务调度、一次发送、超时/停机和归属检查；只依赖明确Store/快照/sender协议。
- 专用邮件DTO/Sender、配置及异常映射：独立用途、脱敏和外部化。

沿用user模块及现有Java21/Spring/Redis/MySQL/JavaMail技术栈。预计新增配置、专用Lua/邮件/服务/测试及文档，只追加必要SecurityConfig公开路径、Repository投影与异常映射；无新业务表、Flyway迁移、依赖或Compose服务。不得为复用重构既有验证码、邮件流程、密码策略和JWT组件。具体文件及协议签名在writing-plans固定。

## 10. 验证与完成条件

- MVC与Reader：无登录申请、202字段及no-store；未知/重复/转义键、空值、字符和长度、UTF-8、16384/16385、415；错误code/type/Retry-After及OpenAPI真实生成契约。
- Service单测：准入先于查询、最小快照及无账户同路径、入队未知不自动重试、额度不退、隐私字段不泄漏；不以过时或伪造JWT改变目标账户。
