# 登录认证版本绑定部署说明

适用范围：现有 `POST /api/v1/auth/login` 的凭据验证结果与管理员 Ticket 版本绑定加固，不新增接口、配置项、数据库迁移或 Redis 服务。

## 安全保证与发布条件

新代码将验证时的账户角色和 token version 传递到后续复核与签发，禁止在旧验证或 Ticket 失效后改用数据库新版本继续登录。JWT 仍沿用既有声明、算法及逐请求数据库版本检查。

所有提供初始登录与 ROLE_SELECTION 兑换的实例必须完成升级，旧实例必须停止或从登录流量中切走，才能宣告该保证生效。仅部分实例升级不满足 U03 修改密码的实施前置条件。

旧实例可能签发无版本 Ticket，也可能忽略新版 Ticket 的版本字段，不能通过继续接受旧格式票据解决混合部署风险。应安排受控切流或短暂停止登录流量，确认不存在旧版本登录处理实例和遗留旧登录处理请求后，再恢复完整登录流量。

## Ticket 与 Redis

- 随机 Ticket、SHA-256 key 派生、music:auth:login-ticket: 命名空间和最长 300 秒有效期不变。
- 新票据用一次 Lua 发布完整四字段和 TTL；新代码不接受缺版本、缺字段、多余字段、非法版本或无有效 TTL 的记录。
- 合法版本 0 不等于版本缺失，不默认填 0 或当前数据库版本。发布期间既有旧 Ticket 可能失效，用户重新登录即可。
- 不清空整个 Redis，不删除其他验证码、登录限流、认证或业务 key；无需迁移、改写或扫描升级旧票据。
- Ticket 一次性消费，后续版本/权限/存储/签发失败不恢复。验证码也保留一次性语义；故障时用户按现有流程重新获取凭据。
- Redis 请求超时可能已产生写入或消费；服务端返回存储不可用，不承诺自动回滚。Lua 对其他请求的原子可见性不意味着跨 MySQL/Redis 事务或错误自动撤销。

## 并发边界

复核之前发生版本或角色变化，初始登录返回 401 INVALID_CREDENTIALS，Ticket 兑换返回 401 LOGIN_TICKET_INVALID。普通初始登录在验证后账户消失也使用 INVALID_CREDENTIALS，不能要求客户端按旧路径的 Ticket 错误码处理。

最终复核之后仍可能发生撤销。此时可能返回旧版本 JWT 或 Ticket：JWT 后续受保护请求返回 TOKEN_REVOKED，Ticket 兑换无法升级为新版本有效 JWT。此保证不等于中断所有已通过认证的业务请求或媒体传输，也不保证登录请求本身总是即时 401。

保留既有登录限流，不新增或重置计数；版本失配走原有认证失败计数路径。不要通过自动恢复 Ticket、自动重试消费或缓存旧验证结果掩盖故障。

## 回滚

没有数据库迁移需要回滚，但回滚到旧登录代码会重新引入旧验证结果/Ticket 换取新版本有效 Token 的风险。回滚时必须同步停止宣称加固已生效，并停止依赖该保证的改密上线流程；不能仅凭旧 Token 仍有版本字段认为前置条件成立。

## 验证与记录

实施送审需包含真实 MySQL/Redis/BCrypt/JWT 的成功回归、验证后撤销、Ticket 签发后撤销、最终复核后撤销、旧票据/无 TTL 拒绝、规范版本和一次性消费验证。

独立代码审核 accepted 仅代表实现满足审核要求，部署方仍须完成全实例升级与切流检查。记录实际实现提交与部署版本；U03 计划以 accepted 的代码基线为依据，实际环境保证以此部署条件为前提。
