## 1. 状态与优先级

- 待设计：已记录需求，尚未确认接口契约。下表未完成任务默认以此状态登记，实际进度以第 8 节跟踪表为准。
- 待实现：设计已确认；开发中：正在实现；待审核：代码、文档及必要检查完成；已完成：独立审核 accepted。
- P0：正式对外使用前必须解决的安全或数据可靠性事项。
- P1：核心使用链路，或在高频访问前需要完成的能力。
- P2：管理、账户体验及运营维护能力，可在核心链路稳定后完成。
- P3：按实际使用和测量结果决定的增强项。

P0 是上线门槛，不代表必须在本地核心功能开发前全部实现。若现有部署、备份或告警已经满足要求，相应任务可通过验证与文档补齐完成，避免重复建设。

## 3. 用户与账户

基本资料与安全资料分开处理：用户名通过基本资料接口修改；邮箱变更必须经过专用验证流程，不能直接通过资料接口覆盖。

| 编号 | 优先级 | 任务 | 建议接口 | 简要说明 |
| --- | --- | --- | --- | --- |
| U01 | P1 | 获取当前用户信息 | `GET /api/v1/users/me` | 从认证主体确定本人，返回允许展示的账户资料和角色信息，不接受前端用户 ID 代替身份，不返回密码摘要等内部字段。 |
| U02 | P2 | 修改个人资料 | `PATCH /api/v1/users/me` | 先支持现有用户名字段，处理规范化、长度和唯一性；昵称等新字段是否需要另行确认。邮箱不在此接口直接修改。 |
| U03 | P1 | 修改密码 | `PUT /api/v1/users/me/password` | 已登录本人校验原密码后设置新密码；配合 token version 撤销策略，明确当前及其他登录是否继续有效。 |
| U04 | P1 | 发起邮箱变更并验证新邮箱 | `POST /api/v1/users/me/email-change-requests` | 对本人进行近期身份验证，向新邮箱发送专用验证码；校验邮箱可用性、限流和发送失败，验证码绑定用户及目标邮箱，不提前修改邮箱。 |
| U05 | P1 | 确认邮箱变更 | `POST /api/v1/users/me/email-change-confirmations` | 验证新邮箱验证码后原子更新；处理邮箱并发占用、验证码一次消费及认证状态变更，可通知原邮箱。依赖 U04。 |
| U06 | P1 | 发起找回密码 | `POST /api/v1/auth/password-reset-requests` | 为未登录用户发送专用找回凭证，统一对外响应，避免枚举注册邮箱；独立限流，不复用 LOGIN 用途验证码。 |
| U07 | P1 | 完成密码重置 | `POST /api/v1/auth/password-resets` | 校验有时效且一次性使用的找回凭证，更新密码并撤销既有认证状态；覆盖重复提交、并发与过期。依赖 U06。 |
| U08 | P2 | 获取本人登录历史 | `GET /api/v1/users/me/login-history` | 分页展示时间、结果、登录方式和必要设备信息；先在现有登录流程建立审计记录，设定保留期限及 IP 等信息的脱敏规则。 |
| U09 | P1 | 退出全部登录 | `POST /api/v1/auth/logout-all` | 通过版本递增撤销本人全部现有 Token，明确撤销何时生效；前端删除 Token 不等同于服务端撤销。依赖统一认证状态更新机制。 |
| U10 | P2 | 退出当前登录 | `POST /api/v1/auth/logout` | 仅撤销当前会话，不影响其他设备；需先设计 jti 或会话标识及有效期内撤销记录，与 U09 区分语义。 |
| U11 | P3 | Token 续期 | `POST /api/v1/auth/refresh` | 先确认是否需要长期登录；如引入刷新凭证，必须设计轮换、重放检测、撤销和安全存储，不能仅延长旧 JWT。 |

## 4. 歌曲

所有普通用户歌曲入口保持登录要求，只能访问 PUBLISHED；管理员是否可查看其他状态应在各接口独立确认。详情接口的管理员全状态可见规则，不自动等于允许播放未发布音频。

| 编号 | 优先级 | 任务 | 建议接口 | 简要说明 |
| --- | --- | --- | --- | --- |
| T01 | P1 | 获取歌曲封面 | `GET /api/v1/tracks/{trackId}/cover` | 与已上线详情 cover.url 对齐，鉴权后从私有 S3/MinIO 流式读取；明确缺封面、对象缺失、存储故障与缓存策略。普通图片读取的 Range 支持按需要设计，不机械套用音频要求。 |
| T02 | P1 | 分页歌曲列表 | `GET /api/v1/tracks` | 提供统一 page、size、sort，限制最大页大小及排序字段，返回列表 DTO 和可空封面信息，排除普通用户不可见状态，避免 N+1。 |
| T03 | P1 | 歌曲播放 | `GET /api/v1/tracks/{trackId}/stream` | 按既有后端代理方案流式读取，支持 Range、206、416、Accept-Ranges、Content-Range、ETag 等；验证请求中断、对象缺失及代理超时，不完整加载音频到内存。 |
| T04 | P1 | 歌曲搜索 | `GET /api/v1/tracks/search` | 按标题、艺术家、专辑搜索并分页，限制关键词长度和查询成本；确认中文匹配方式及索引策略，不默认引入搜索引擎。 |
| T05 | P2 | 管理员歌曲列表 | `GET /api/v1/admin/tracks` | T02 已规划统一状态筛选；仅在需要额外管理字段或新筛选时单独设计，不重复建设现有状态列表。 |
| T06 | P2 | 管理员替换封面 | `PUT /api/v1/tracks/{trackId}/cover` | 确认允许修改的歌曲状态；验证文件大小、MIME、扩展名和魔数，创建新资产并处理旧对象清理、并发和失败补偿。 |
| T07 | P2 | 编辑已发布歌曲元数据 | `PATCH /api/v1/tracks/{trackId}/metadata` | 如实际需要，单独设计标题、艺术家、专辑等字段的在线修改及版本冲突；不顺手扩大现有草稿编辑接口权限。 |
| T08 | P3 | 恢复归档歌曲 | `POST /api/v1/tracks/{trackId}/restore` | 仅在确认需要时实施；先决定恢复到 DRAFT 还是 PUBLISHED，并验证媒体资产存在及状态并发，不能默认恢复即公开。 |

搜索可选合入列表查询参数 `GET /api/v1/tracks?q=...`；T02/T04 是需求分项，路径方案确认后再决定是否由一个接口实现，不能重复建设两套查询逻辑。

## 7. 建议推进顺序

1. 完成最小音乐浏览与播放闭环：T01 封面 → T02 列表 → T03 播放 → T04 搜索，同时补 U01 当前用户信息。
2. 在高频访问或扩大使用前，推进 O09 性能基线和 O01 认证状态优化；O01 的状态写入规则作为后续密码/邮箱/禁用任务的共同约束。
3. 完善账户安全：U03 修改密码、U06/U07 找回密码、U04/U05 改邮箱验证、U09 全部退出，配套 O02；每个接口分别设计与审核。
4. 正式对外使用前完成 O03/O04 上线门槛，核验 O05 媒体补偿。
5. 按需求补 U02 资料、U08 历史、T05 管理列表、A01 用户列表等管理体验，再处理其余 P2/P3。

这不是必须串行等待的跨任务依赖图；同一开发变更仍遵守单接口规则。O07/O08 可作为独立小任务择机处理，不阻塞已 accepted 的详情接口。
